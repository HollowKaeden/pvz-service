# pvz-service

Сервис для сотрудников пунктов выдачи заказов (ПВЗ): приёмка товаров. Решение открытого [тестового задания Авито для бэкенд-стажёров, весна 2025](https://github.com/avito-tech/tech-internship/blob/main/Tech%20Internships/Backend/Backend-trainee-assignment-spring-2025/Backend-trainee-assignment-spring-2025.md).

Учебный и портфолио-проект: в Авито решение не отправлялось.

> **Статус:** все ручки из контракта работают, включая регистрацию и вход по email. Есть gRPC, Prometheus и интеграционные тесты. Закрытие приёмки запускает начисление в отдельном billing через outbox и Kafka. Панель показывает баланс, журнал и время доставки. Billing проверен локально и на демо-сервере. В `/docs/` переключаются две спецификации.

**Демо:** https://pvz.givemeanoffer.ru — страница, где весь сценарий приёмки проходится мышкой, а каждый запрос к API виден в журнале. Swagger UI: https://pvz.givemeanoffer.ru/docs/. gRPC на том же адресе, вызвать его можно через [grpcurl](https://github.com/fullstorydev/grpcurl):

```bash
grpcurl pvz.givemeanoffer.ru:443 pvz.v1.PVZService/GetPVZList
```

Данные демо сбрасываются каждую ночь: остаются три ПВЗ, в Москве одна приёмка открыта.

## Запуск

Нужны Go 1.27+ и Docker.

```bash
cp .env.example .env          # локальные настройки
make up                       # PostgreSQL, Kafka, Prometheus, Caddy в Docker
make run                      # pvz; миграции применяются при старте
# Во втором терминале:
make run-billing              # своя БД, consumer, API :8081 и метрики :9001
curl localhost:8000/health    # {"status":"ok"}
curl localhost:8000/billing/health
```

Единый вход через Caddy: http://localhost:8000/, Swagger UI: http://localhost:8000/docs/. Порты приложений остаются 8080 и 8081, но для панели начислений нужен общий origin на 8000. Чтобы вызывать закрытые ручки ПВЗ, получите токен в `POST /dummyLogin` и вставьте его в окно **Authorize**. Начисления доступны без входа. Если `.env` остался от старой версии, добавьте переменные `BILLING_*` из `.env.example` (и поправьте порт БД, если он отличается от 5432). `make up` создаёт отдельную локальную БД billing и на существующем volume.

gRPC слушает порт 3000: `grpcurl -plaintext localhost:3000 pvz.v1.PVZService/GetPVZList`.

Метрики: http://localhost:9000/metrics. Prometheus из `make up` забирает их каждые 5 секунд, его страница: http://localhost:9090. Примеры запросов:

```promql
# запросов в секунду по маршрутам
sum by (route) (rate(pvz_http_request_duration_seconds_count[1m]))
# доля ответов быстрее 100 мс
sum(rate(pvz_http_request_duration_seconds_bucket{le="0.1"}[5m])) / sum(rate(pvz_http_request_duration_seconds_count[5m]))
# время ответа, в которое укладываются 99% запросов
histogram_quantile(0.99, sum by (le) (rate(pvz_http_request_duration_seconds_bucket[5m])))
```

### Настройки

Только через переменные окружения. Обязательны `DATABASE_URL` и `JWT_SECRET`, у остальных есть значения по умолчанию. `make` берёт переменные из файла `.env`.

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `DATABASE_URL` | — | подключение к PostgreSQL, например `postgres://user:pass@localhost:5432/pvz` |
| `JWT_SECRET` | — | ключ подписи токенов, не короче 32 байт (`openssl rand -hex 32`) |
| `DB_MAX_CONNS` | `10` | максимум соединений; в локальном `.env.example` — 20, в проде — 5 |
| `MIGRATE_ON_START` | `false` | применять миграции при запуске |
| `HTTP_ADDR` | `:8080` | адрес HTTP API |
| `GRPC_ADDR` | `:3000` | адрес gRPC-сервера |
| `METRICS_ADDR` | `:9000` | адрес, на котором Prometheus забирает метрики (`/metrics`) |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `TRUSTED_PROXIES` | пусто | IP или подсети прокси через запятую, которым сервис верит в `X-Forwarded-For` (на сервере это Caddy) |
| `AUTH_RATE_LIMIT` | пусто (без лимита) | сколько запросов к `/register` и `/login` пропускать с одного IP, например `10/1m` (10 в минуту) |
| `KAFKA_BROKERS` | пусто | брокеры через запятую (`localhost:9092` локально, `kafka:19092` в проде); без переменной relay выключен, события остаются в outbox |
| `KAFKA_TOPIC` | `pvz.reception.closed` | топик закрытых приёмок |
| `BILLING_DATABASE_URL` | — | собственная БД `pvz_billing` со своим пользователем; единственная обязательная настройка billing |
| `BILLING_DB_MAX_CONNS` | `3` | 3–10 соединений, одно держит блокировку процесса |
| `BILLING_MIGRATE_ON_START` | `true` | миграции billing перед запуском |
| `BILLING_HTTP_ADDR` / `BILLING_METRICS_ADDR` | `:8081` / `:9001` | API и отдельный порт метрик |
| `BILLING_CONSUMER_GROUP` | `pvz-billing` | независимые offsets подписчика |

Billing не требует `JWT_SECRET`. Для него `KAFKA_BROKERS` по умолчанию `localhost:9092`.

## Разработка

```bash
make up         # поднять зависимости и Caddy (make down — остановить)
make migrate    # применить миграции обеих БД без запуска сервисов
make test       # unit-тесты с -race, без базы и Docker
make test-int   # интеграционные тесты: PostgreSQL и Kafka в Docker
make cover      # покрытие unit- и интеграционными тестами, падает ниже 75%
docker build -t pvz-service .   # образ, как на сервере
make lint       # golangci-lint: формат и линтеры
make fmt        # gofmt + goimports
make generate   # кодогенерация (oapi-codegen, buf, mockery), результат коммитится
make hooks      # один раз: pre-commit hook с линтером
```

golangci-lint ставится отдельным бинарником ([инструкция](https://golangci-lint.run/docs/welcome/install/)), версия v2.14.0, как в CI. Для `-race` нужен cgo: на Linux и macOS работает из коробки, на Windows нужен gcc (например, MinGW-w64).

Генераторы кода указаны в `go.mod` и запускаются через `go tool`, поэтому ставить их отдельно не нужно, а версии везде одни. Это касается и gRPC: код из `pvz.proto` генерирует [buf](https://buf.build) с плагинами `protoc-gen-go` и `protoc-gen-go-grpc`, отдельный protoc не нужен.

CI (`.github/workflows/ci.yml`) на каждый push в `main` и PR запускает линтер, unit- и интеграционные тесты, проверяет покрытие и то, что сгенерированный код совпадает со схемой, и применяет миграции к настоящему PostgreSQL.

Интеграционные тесты сами поднимают PostgreSQL и Kafka в Docker через [testcontainers](https://golang.testcontainers.org/). На Windows с Docker Desktop нужны две переменные окружения, их задаёт `Makefile`. Поэтому запускайте тесты через `make`, а не через `go test` напрямую.

## Нагрузка

Цель задания проверяется локально: 1000 RPS, p99 ≤ 100 мс, успешность ≥ 99,99%. `make load` запускает наш [http-loadgen](https://github.com/HollowKaeden/http-loadgen) из соседнего репозитория. `cmd/pvz-load` получает токены через `/dummyLogin`, готовит данные публичным API и сохраняет JSON-отчёты без токенов. В ядро генератора изменений не требуется.

Два отдельных сценария по 30 секунд:

- Чтение: `GET /pvz`, страница из 10 ПВЗ, у каждого одна закрытая приёмка с 50 товарами. Фильтр по датам фиксирует этот набор; ответ содержит около 83 КБ JSON. Перед измерением — 3 секунды прогрева. Повторный запуск проверяет размер и состав сохранённого fixture, поэтому пустая БД не даст случайно хороший результат.
- Запись: `POST /products`, 10 независимых ПВЗ, по 1/10 общего RPS на каждый, суммарно 100 воркеров. После прогона приёмки закрываются; начисление каждой должно точно совпасть с числом ответов 201. Эти проверки не входят в измеряемое время. Число товаров в приёмке ограничено, чтобы закрытие укладывалось в лимит события Kafka.

Скорость задаётся `-rps` (open-loop). Инструмент проверяет фактическую скорость отдельно от латентности: нужно получить не меньше 99% заданного RPS, p99 ≤ 100 мс и ≥ 99,99% ответов ожидаемого кода. Иначе команда завершается с ошибкой. Запись идёт несколькими процессами CLI: их перцентили не усредняются, в отчёте показан **худший p99 потоков**, а общий RPS считается по общему времени. Первичные отчёты каждого потока сохранены внутри итогового JSON.

### Повторить локально

```bash
# Остановите make run и make run-billing, если они занимают порты.
make load-up     # зависимости + Linux pvz/billing из CI-образа
make load        # CLI на хосте → HTTP :8080, billing :8081

# На Windows используйте Git Bash. Для сопоставимого Linux-окружения:
make load-linux LOAD_ARGS="-rps 1020"
# Отчёт: tmp/load-linux/results/summary.json

make load-down   # остановить только pvz/billing; make down — всё окружение
```

`load-up` использует `PVZ_LOAD_IMAGE` (по умолчанию последний CI-образ). При смене ревизии сначала выполните `docker compose -f compose.yaml -f compose.load.yaml pull pvz billing`. Чтобы проверить изменённый код до пуша, соберите образ локально: `docker build -t pvz-service:load .`, затем `make load-up PVZ_LOAD_IMAGE=pvz-service:load`. Пулы локального контейнера задаёт `LOAD_DB_MAX_CONNS` (20 по умолчанию); prod-конфигурацию это не меняет.

Для запуска через `make run` отдельный контейнер приложения не нужен: `make up`, `make run DB_MAX_CONNS=20`, во втором терминале `make run-billing`, затем `make load`. Ключи сценария передаются через `LOAD_ARGS`: `-profile list|products|all`, `-rps`, `-duration`, `-warmup`, `-workers`, `-writers`, `-out`. При проверке другой машины используйте отдельный `-out`; fixture переживает запуски, но не сброс БД. Для остановки — Ctrl+C. Данные создаются в новых ПВЗ, существующие не очищаются.

## События: outbox и Kafka

Закрытая приёмка — факт, который могут использовать начисления, уведомления и аналитика. Открытая приёмка ещё меняется: сотрудник вправе удалить последний товар. Поэтому публикуется только `reception.closed`, уже с окончательным составом.

```text
закрытие приёмки → PostgreSQL (статус + outbox одной транзакцией)
                                    ↓ relay
                                  Kafka → billing → своя БД (журнал + балансы)
```

- Событие содержит UUID, тип, версию, время, ПВЗ, город, даты открытия и закрытия и товары (`id`, `type`). JSON-контракт — `internal/eventschema`. Данных достаточно для подписчика без запросов обратно в pvz.
- Состав читается одним запросом под той же блокировкой приёмки, которая защищает добавление и удаление товара. Пустую приёмку закрыть нельзя. Если JSON события больше 900 КиБ, закрытие возвращает 400 с предложением удалить последние товары: непосильное для Kafka сообщение не задержит всю очередь.
- Закрытие и запись в outbox либо коммитятся вместе, либо вместе откатываются. Kafka из HTTP-запроса не вызывается. `/health` проверяет только Postgres.
- Relay берёт по одной записи в порядке id: `FOR UPDATE SKIP LOCKED`, отправка через [franz-go](https://pkg.go.dev/github.com/twmb/franz-go/pkg/kgo), затем отметка `sent_at`. Работает один экземпляр relay. Пока сообщение не подтверждено, он не переходит к следующему.
- Доставка **at-least-once**. Если Kafka приняла сообщение, а коммит БД упал, relay отправит тот же JSON и UUID ещё раз. Подписчик обязан убирать дубли по UUID события. Идемпотентный producer сам по себе эту границу Kafka/Postgres не закрывает.
- Недоступный брокер не мешает API: события ждут в outbox. Попытка доставки ограничена 5 с, пауза после ошибок растёт от 1 до 30 с. Пустая очередь опрашивается раз в секунду. При остановке процесса relay отменяется вместе с серверами.
- Ключ сообщения — `pvz_id`: при неизменном числе партиций события одного ПВЗ попадают в одну партицию в порядке отправки. В топике три партиции и одна реплика: демо не защищено от потери диска брокера.
- [Хранение Kafka](https://kafka.apache.org/41/configuration/topic-configs/): сутки или 32 МиБ на партицию, сегменты по 8 МиБ, смена сегмента не реже часа. Удаление идёт целыми сегментами и с задержкой проверки; эти настройки не являются жёсткой дисковой квотой. Те же значения заданы брокеру по умолчанию для будущих топиков.
- Отправленные записи outbox хранятся сутки; раз в минуту удаляется до 1000 записей. Неотправленные не удаляются. `pvz_outbox_pending` показывает очередь при включённом relay.

Топик создаёт relay при первой отправке. В compose автоматическое создание случайных топиков выключено. Повторное создание существующего топика безопасно; смена `KAFKA_TOPIC` предназначена для нового потока, а не для переноса уже отправленной истории.

Индексы outbox проверены через `EXPLAIN (ANALYZE, BUFFERS)` на PostgreSQL 16: 20 000 записей, из них 10 неотправленных и 10 отправленных старше суток. Поиск следующего сообщения использует `outbox_pending_idx` (0,022 мс), поиск записей для очистки — `outbox_sent_idx` (0,024 мс). Это локальный замер с прогретым кешем. Оба запроса обходятся без чтения всей таблицы и отдельной сортировки.

Проверка локально: запустите сервис с `KAFKA_BROKERS` из `.env.example`, закройте приёмку через интерфейс и прочитайте топик:

```bash
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka:19092 --topic pvz.reception.closed --from-beginning \
  --property print.key=true
```

Можно остановить брокер (`docker compose stop kafka`), закрыть ещё одну приёмку и вернуть его (`docker compose start kafka`). API продолжит работать, а очередь после возвращения брокера уйдёт в топик. Автоматические тесты проверяют этот сценарий с настоящей Kafka, откат записи outbox и повтор после неуспешного коммита.

В проде брокер доступен только внутри сети `db`, с heap 256 МиБ и лимитом контейнера 512 МиБ. После изменений проверяются `free -m` (available ≥ 500 МиБ), `docker stats --no-stream`, подкачка и отсутствие OOM. Если памяти мало, сначала уменьшить heap до 192 МиБ.

Проверено на демо-сервере 4 ноября 2026 (до добавления billing): закрытие тестовой приёмки создало событие в outbox, из Kafka прочитан тот же UUID и состав товаров, очередь пуста. После проверки Kafka занимала ~346 МиБ, pvz ~7,5 МиБ; доступно 917 МиБ RAM, swap 76 из 2047 МиБ без активной подкачки. Оба контейнера healthy, без OOM и перезапусков. HTTP и gRPC через Caddy работают; метрики и порты Kafka снаружи не опубликованы.

## Начисления: отдельный подписчик

Billing не читает таблицы pvz и не вызывает его API. Общий пакет только один — `internal/eventschema`. Собственная БД, миграции, конфигурация и метрики находятся в `internal/billing`. В одном Docker-образе два бинарника: `pvz` и `billing`; у контейнера billing свой entrypoint.

За электронику начисляется 100 ₽, за одежду 50 ₽, за обувь 30 ₽. Ставки лежат в `rates`, процесс читает их при запуске. Все суммы — целые копейки (`bigint`), без округления денег через float. Смена ставок требует рестарта billing; старые суммы изменяются только при явном rebuild.

Сумма считается по снимку товаров в памяти. На событие выполняются два SQL-запроса в одной транзакции: `INSERT payouts ON CONFLICT DO NOTHING`, затем UPSERT баланса. Уникальный `event_id` отбрасывает повтор, в том числе при конкурентной обработке. Offset Kafka коммитится **после** транзакции БД. Если между этими операциями процесс упадёт, повтор не начислит деньги второй раз. Так получается однократный эффект поверх доставки at-least-once.

Consumer читает по одному сообщению с ручным коммитом и блокирует ребалансировку до завершения обработки ([документация franz-go](https://pkg.go.dev/github.com/twmb/franz-go/pkg/kgo#BlockRebalanceOnPoll)). Битый JSON, неизвестная версия или товар без ставки после трёх попыток отправляются в `<topic>.dlq`. В headers сохраняются ошибка, исходный топик, партиция, offset и время. Только после подтверждения DLQ коммитится исходное сообщение. Недоступная БД ждёт восстановления с паузой 250 мс → 5 с, без лимита попыток и без DLQ. В этой небольшой реализации ожидание задерживает весь consumer, а не только проблемную партицию. API продолжает работать при недоступной Kafka; health проверяет только собственную БД.

Публичный API чтения описан в `api/billing.yaml` и генерируется отдельно от контракта Авито:

- `GET /billing/payouts?page=1&limit=10` — балансы, порядок по UUID ПВЗ;
- `GET /billing/payouts/{pvzId}?page=1&limit=30` — журнал, новые начисления сверху;
- `GET /billing/rates` — ставки текущего процесса;
- `GET /billing/health` — доступность БД.

`page` от 1 до 10 000, `limit` от 1 до 30. До первого начисления журнал пуст. Здесь нет авторизации ради публичного демо; в настоящем сервисе права ограничивали бы владельцем ПВЗ. Фронт не пересылает токен pvz в billing. После закрытия приёмки он до 20 секунд опрашивает журнал и показывает `processed_at − closed_at`; при задержке можно обновить вручную. Запросы видны в общем журнале.

Индекс `(pvz_id, processed_at DESC, event_id DESC)` проверен на PostgreSQL 16 с 10 000 записями: `Index Scan using payouts_pvz_processed_idx`, без отдельной сортировки, 4 shared buffers, 0,022 мс на прогретом кэше. Интеграционный тест повторяет EXPLAIN; время зависит от машины.

### Пересчёт и ночной сброс

`billing rebuild` очищает журнал и балансы и устанавливает offsets группы в начало **сохранившейся** истории. Это не восстановление всей истории: retention в демо — сутки. Сначала остановите billing (`Ctrl+C` в его терминале), затем:

```bash
make billing-rebuild
make run-billing
```

После запуска consumer заново начислит события. При тех же ставках балансы совпадут. Работающий consumer исключён advisory-lock в БД и проверкой отсутствия участников Kafka-группы. Освобождение блокировки подтверждается запросом `pg_advisory_unlock` до возврата соединения в пул; это работает и после отмены контекста при shutdown. Очистка проекции и намерение сменить offsets коммитятся вместе; если процесс упадёт до подтверждения Kafka, следующий старт завершит операцию по таблице `pending_reset`.

`billing demo-reset` очищает проекцию и переводит offsets в **конец** топика: вчерашние события не начислятся снова. Ночной скрипт из `portfolio` останавливает pvz и billing, выполняет billing reset, затем pvz reset и возвращает процессы даже при ошибке. Во время сброса демо кратко недоступно. Эталон pvz создаётся через его сервисы, и новые начисления приходят обычным путём. Справочники не очищаются. Проект в бэкап не входит.

### Метрики и DLQ

На `:9001/metrics`: `billing_events_processed_total`, `billing_duplicates_total`, `billing_accrued_kopecks_total`, `billing_consumer_lag{partition}`, `billing_dlq_total` (отправки за время процесса), `billing_dlq_size` (сохранившиеся сообщения) и `billing_http_request_duration_seconds` с шаблоном маршрута. Лаг и размер DLQ обновляются раз в 15 с; Prometheus из локального compose собирает оба сервиса.

Переотправка из DLQ ручная. Сначала выясните причину по headers и исправьте событие или ставку/код. Прочитайте **одну** нужную запись (пример: partition 0, offset 0), без headers в stdout:

```bash
docker compose exec -T kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka:19092 --topic pvz.reception.closed.dlq \
  --partition 0 --offset 0 --max-messages 1 \
  --property print.key=true --property 'key.separator=|' > dlq-record.txt
# Проверьте/исправьте JSON в dlq-record.txt. Сохраните исходные id и ключ pvz_id.
docker compose exec -T kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka:19092 --topic pvz.reception.closed \
  --property parse.key=true --property 'key.separator=|' < dlq-record.txt
```

Каждая строка должна оставаться `pvz_id|JSON` без переносов внутри JSON. Обработанное событие с тем же UUID будет пропущено. DLQ не очищается переотправкой: запись удалит retention. Не запускайте массовую переотправку без проверки причин.

Локальные тесты с настоящими Postgres и Kafka проверяют: закрытие → outbox → начисление; конкурентный дубль и откат транзакции; rebuild с теми же балансами; битое сообщение → DLQ → следующее начисление; отключённая БД без DLQ; ночной сброс без повторного начисления вчерашних событий; восстановление незавершённого reset.

Проверено на демо-сервере 5 ноября 2026: pvz и billing работают из одного образа ревизии `061e4f5`, конфигурация деплоя — `35bb707`. На отдельном ПВЗ созданы три товара, последний удалён, приёмка закрыта. UUID события совпал в outbox и журнале billing; за оставшиеся электронику и обувь начислено ровно 13 000 копеек одной записью, баланс — 130 ₽. От закрытия до начисления прошло 756 мс. Очередь outbox, lag всех партиций и DLQ равны нулю; незавершённых reset нет. Роли pvz и billing не могут подключаться к чужой БД. HTTP health, gRPC и обе спецификации Swagger доступны; опубликованный фронт совпадает с коммитом, внешние порты метрик закрыты.

После проверки billing занимал ~4,7 МиБ из 64, pvz ~6,3 МиБ из 128, Kafka ~341 МиБ из 512; доступно 943 МиБ RAM, swap 143 из 2047 МиБ. При замерах записи в swap не было, отмечены единичные чтения 16–24 КиБ/с. Все три контейнера healthy, без OOM и перезапусков. Ночной reset установлен на 04:10; скрипт и конфигурация на сервере совпадают с репозиторием. Сам reset и rebuild проверены интеграционными тестами. Проверочный ПВЗ остаётся до планового ночного сброса.

## Контракт

- `api/openapi.yaml` — HTTP API. Это копия `swagger.yaml` из задания, она не меняется.
- `api/pvz.proto` — gRPC, тоже копия из задания. Изменена одна строка, `go_package`: в задании там заглушка, и её просят заменить на путь в своём проекте.

Код генерируется командой `make generate`: HTTP-слой из `openapi.yaml` в `internal/transport/http/oapi`, gRPC из `pvz.proto` в `internal/transport/grpc/pvzv1`. Руками его не правят.

## Вопросы по заданию и решения

**Роли.** В тексте задания обычный пользователь называется `client`, а в swagger — `employee`. Я следую swagger: роли `employee` и `moderator`.

**Токены.** `/dummyLogin` выдаёт JWT с ролью, он действует 24 часа. Подпись проверяется ключом из `JWT_SECRET`, и принимается только алгоритм HS256: токен без подписи или с другим алгоритмом не пройдёт.

**Регистрация и вход.** `/register` заводит пользователя с email, паролем и ролью, `/login` проверяет пароль и выдаёт такой же токен, как `/dummyLogin`, с ролью пользователя. `/dummyLogin` остаётся, как требует задание.

- Пароль хранится только как хеш bcrypt. Сам пароль не попадает ни в базу, ни в логи.
- Пароль должен быть не короче 8 символов и не длиннее 72 байт. Дальше 72 байт bcrypt пароль не читает, поэтому длинный пароль сервис отклоняет сразу, а не обрезает молча. Латинская буква занимает 1 байт, кириллическая 2.
- Email не зависит от регистра: `Ivan@Example.com` и `ivan@example.com` считаются одним адресом.
- Если email уже занят, ответ 400, как в контракте. Занятость проверяет уникальный индекс в базе, а не отдельный запрос перед записью. Поэтому две одновременные регистрации с одним email не пройдут обе. Проверено так: 10 одновременных регистраций, успешна ровно одна.
- Неверный пароль и неизвестный email дают один и тот же ответ: 401 «неверный email или пароль». Ответ на неизвестный email ждёт столько же, сколько проверка пароля. Иначе по ответу или по его скорости можно было бы узнать, кто зарегистрирован.
- Можно ограничить число запросов к `/register` и `/login` с одного IP (переменная `AUTH_RATE_LIMIT`, на демо 10 в минуту). Это защита от перебора паролей. Сверх лимита ответ 429 с заголовком `Retry-After`. В контракте 429 нет, но по правилам HTTP это он. Остальные ручки лимит не трогает, иначе он мешал бы нагрузочному тесту. Счётчики хранятся в памяти сервиса и обнуляются при перезапуске.

**gRPC.** Метод `GetPVZList` отдаёт все ПВЗ: id, дату регистрации и город, новые сверху. Задание просит именно все, поэтому страниц здесь нет. Токен не нужен, как и сказано в задании. Сервер слушает порт 3000 и работает в одном процессе с HTTP: останавливаются они тоже вместе. Включён reflection: grpcurl сам узнаёт методы сервера, proto-файл ему не нужен. Если что-то сломалось внутри, клиент получает код `Internal` с общим текстом, а подробности пишутся в лог, как с ответом 500 в HTTP. На демо gRPC идёт через тот же адрес и порт 443, что и сайт: прокси отличает gRPC-запросы по типу тела.

**Права доступа.** Какой роли доступна какая ручка, записано в одной таблице рядом с маршрутами. Права проверяются раньше, чем разбирается тело запроса. Если ручки в таблице нет, она закрыта для всех. Отдельный тест сверяет таблицу с контрактом: защищённые там ручки должны быть защищены и в коде.

**Коды ответа без доступа.** Если токена нет или он неверный, сервис отвечает 401: он не знает, кто делает запрос. Если токен верный, но роли действие не разрешено, ответ 403. В контракте у закрытых ручек описан только 403, но по правилам HTTP эти два случая различаются, поэтому я добавил 401.

**Кодогенерация.** Задание просит генерировать DTO по схеме. Я использую [oapi-codegen](https://github.com/oapi-codegen/oapi-codegen): он генерирует не только DTO, но и разбор запросов и типы ответов. Поэтому ручка не может вернуть ответ, которого нет в схеме. Сгенерированные типы используются только в HTTP-слое, бизнес-логика работает со своими.

**Названия констант.** Города и типы товаров в схеме записаны по-русски, и генератор сделал бы константы вида `Москва`. Чтобы не менять схему, латинские имена (`CityMoscow`, `ProductTypeElectronics`) заданы в отдельном файле `oapi/overlay.yaml`. В JSON значения остаются русскими, как в задании.

**Ошибки.** Все ошибки возвращаются в формате из схемы: `{"message": "..."}`. Если запрос не удаётся разобрать (сломанный JSON, неверный UUID или дата), сервис отвечает 400. Если нарушено правило (например, роль не `employee` и не `moderator`), сервис отвечает понятным текстом, а код ответа для каждого правила задан в одном месте HTTP-слоя. Непредвиденные ошибки пишутся в лог, а клиент получает 500 без подробностей.

**Swagger UI** открывается на `/docs/`. Это одна HTML-страница, скрипты грузятся с CDN. В схеме не указан адрес сервера, поэтому запросы из Swagger UI идут туда же, откуда открыта страница: и локально, и на демо-сервере.

**Остановка.** По сигналу остановки (например, `docker stop`) сервис перестаёт принимать новые запросы и даёт текущим до 8 секунд на завершение. Docker ждёт 10 секунд, так что сервис успевает остановиться сам.

**Справочники.** Города, типы товаров и статусы приёмки лежат в отдельных таблицах, а в основных таблицах хранится только ссылка на них. Проверять значения будет сервис, чтобы вернуть понятную ошибку. База отвечает только за целостность данных.

**Одна открытая приёмка.** Уникальный индекс не даёт открыть на одном ПВЗ две приёмки сразу. Это запасная защита: основная проверка будет в сервисе.

**Порядок товаров.** Каждый товар получает порядковый номер, и по нему находится последний добавленный товар для удаления. Время добавления для этого не подходит: у двух товаров оно может совпасть.

**Заведение ПВЗ.** id и дату регистрации назначает сервис. Если клиент прислал их в теле запроса, они не используются: иначе можно было бы завести ПВЗ задним числом или с чужим id.

**Две приёмки сразу.** Допустим, два сотрудника одновременно нажали «открыть приёмку» на одном ПВЗ. Оба запроса проверяют, нет ли уже открытой приёмки. Если они сделают это одновременно, оба ничего не найдут, и откроются две приёмки. Поэтому сервис сначала блокирует запись ПВЗ в базе (`SELECT ... FOR UPDATE`), и только потом проверяет и создаёт приёмку. Второй запрос ждёт, пока первый закончит, и уже видит открытую приёмку. Проверено так: 30 одновременных запросов на один ПВЗ, успешен ровно один.

**Закрытие приёмки.** Сервис находит открытую приёмку ПВЗ и блокирует её до конца операции. Так закрытие не пересечётся с добавлением или удалением товара в той же приёмке.

**Пустую приёмку закрыть нельзя.** Если в приёмке нет товаров, закрытие отвечает 400 «нельзя закрыть приёмку без товаров». В задании это не оговорено. Но приёмка — это товары, которые приехали на ПВЗ, и закрытая приёмка без товаров ничего не значит. Если приёмку открыли по ошибке, в неё просто кладут товары следующей поставки. Удалять приёмку я не стал: такой операции нет в контракте. Проверка идёт под той же блокировкой приёмки, поэтому одновременное удаление последнего товара ей не помешает.

**Товары.** Товар добавляется в открытую приёмку ПВЗ. Тип проверяет сервис по справочнику. Если тип не подходит, в ответе будет список доступных типов.

**Удаление последнего товара.** Удаляется товар, добавленный последним (LIFO). Сервис находит его по порядковому номеру. Добавление, удаление и закрытие сначала блокируют открытую приёмку. Поэтому они не мешают друг другу: приёмку нельзя закрыть посреди добавления товара, а два одновременных удаления не удалят один и тот же товар. Проверено так: в приёмке 10 товаров, 15 одновременных удалений. Ровно 10 удалили по товару, остальные 5 получили ответ «в приёмке нет товаров для удаления».

**Фильтр списка ПВЗ по дате.** В задании сказано: выводить только те ПВЗ, которые в указанный период проводили приёмки. Я понял это так: ПВЗ без приёмок в периоде в список не попадают, а у остальных показываются только приёмки из периода, с товарами. Без фильтра в списке все ПВЗ, даже без приёмок, и все их приёмки. Границы периода входят в него. Можно задать только начало или только конец.

**Порядок в списке.** Новые ПВЗ сверху, внутри ПВЗ новые приёмки сверху, товары в порядке добавления. Если у ПВЗ нет приёмок или у приёмки нет товаров, в ответе пустой список `[]`.

**Параметры списка.** По умолчанию `page=1`, `limit=10`, как в контракте. Если `limit` не от 1 до 30, `page` меньше 1 или начало периода позже конца, ответ 400 с объяснением.

**Список без лишних запросов.** Ответ собирается из трёх запросов к базе, сколько бы ПВЗ ни было на странице. Сначала страница ПВЗ, потом приёмки сразу всех этих ПВЗ, потом товары сразу всех этих приёмок. Если делать отдельный запрос на каждый ПВЗ и каждую приёмку (так называемая проблема N+1), страница из 30 ПВЗ дала бы сотни запросов. Условие фильтра по дате меняется от запроса к запросу, поэтому его собирает [squirrel](https://github.com/Masterminds/squirrel). Остальные запросы написаны обычным SQL.

**Индексы для списка.** Я проверял запросы командой `EXPLAIN ANALYZE` на тестовой базе: 10 000 ПВЗ, 300 000 приёмок, 3 млн товаров. Без новых индексов база читала все ПВЗ, чтобы отдать страницу из 10. С фильтром по дате она перебирала все приёмки. Поэтому добавлены два индекса:

| Запрос | Индекс | Было | Стало |
|---|---|---|---|
| страница ПВЗ без фильтра | `pvz (registration_date, id)` | 3,0 мс | 0,07 мс |
| страница ПВЗ, приёмки за неделю | тот же | 19 мс | 0,16 мс |
| страница ПВЗ, приёмки за час | `receptions (date_time)` | 16 мс | 1,6 мс |

Приёмки и товары страницы и раньше читались по своим индексам: `receptions (pvz_id, date_time)` и `products (reception_id, seq)`. Весь ответ на той же базе занимает 24 мс для 10 ПВЗ (300 приёмок, 3 000 товаров) и 6 мс с фильтром по дате. Почти всё это время уходит на объём ответа, а не на поиск. Чем дальше страница, тем медленнее: базе нужно пропустить все предыдущие ПВЗ. Страница 900 отвечает за 36 мс. Контракт задаёт пагинацию номером страницы, поэтому так и оставлено.

**Ответ, когда ПВЗ нет.** Если ПВЗ с таким id не существует, сервис отвечает 404 «ПВЗ не найден». В контракте у этих ручек 404 нет, там такой запрос считается неверным (400). Но по правилам HTTP это 404, и так клиент отличит опечатку в id от нарушенного правила. Повторное закрытие и закрытие на ПВЗ без открытой приёмки дают 400: «на ПВЗ нет открытой приёмки».

**id записей** — UUID версии 7. В начале такого id стоит время создания, поэтому новые записи добавляются в конец индекса, а не в случайное место.

**Справочник городов** читается из базы один раз при старте сервиса. Город проверяет сервис, и если его нет в справочнике, клиент получает список доступных городов.

**Транзакции** открывает сервис, когда нужно изменить несколько записей сразу. Репозиторий сам транзакций не открывает: если транзакция уже открыта, он выполняет запрос в ней, иначе напрямую.

**Тесты сервисов** работают без базы: вместо репозиториев подставляются моки, их генерирует [mockery](https://github.com/vektra/mockery) (`make generate`).

**Интеграционные тесты** (`tests/integration`) проверяют сервис целиком: HTTP-запросы, сервисы и настоящий PostgreSQL в Docker. Среди них сценарий из задания: завести ПВЗ, открыть приёмку, добавить 50 товаров, закрыть приёмку. Остальные проверяют удаление последнего товара, фильтр и страницы списка ПВЗ и ответ 404 на несуществующий ПВЗ.

**Тесты на гонки.** Несколько тестов шлют одинаковые запросы одновременно:
- 20 попыток открыть приёмку на одном ПВЗ: успешна ровно одна;
- 15 удалений из приёмки с 10 товарами: удалено ровно 10, остальные 5 получили отказ;
- 20 добавлений товара, а посреди них закрытие приёмки: в закрытой приёмке ровно столько товаров, сколько было успешных ответов.

Открытие приёмки защищено дважды: блокировкой в сервисе и уникальным индексом в базе. Чтобы тест проверял именно блокировку, на время теста индекс убирается. Я проверил, что тест работает: без блокировки он падает, потому что открываются все 20 приёмок.

**Покрытие** считается по всем тестам вместе, unit и интеграционным, и сейчас около 92%. В расчёт не входит код HTTP-слоя, который генерирует oapi-codegen: его покрытие ничего не говорит о качестве тестов. Если покрытие станет ниже 75%, CI упадёт.

**Миграции** встроены в бинарник. Их применяет команда `pvz migrate` или сам сервис при старте, если `MIGRATE_ON_START=true`. Если два экземпляра сервиса стартуют одновременно, миграции применит только один.

**Проверка здоровья.** `GET /health` отвечает 200, если база доступна, и 503, если нет.

**Логи** пишутся в JSON, по строке на запрос: метод, путь, статус, время ответа, IP клиента.

**Метрики** для Prometheus сервис отдаёт на отдельном порту 9000 (`/metrics`). На демо-сервере этот порт открыт только внутри Docker-сети, снаружи его не видно.

- Время ответа HTTP и gRPC считается гистограммой по маршрутам и кодам ответа. Число запросов отдельно не считается: оно уже есть в гистограмме (ряд `_count`).
- Маршрут в метрике записан шаблоном: `POST /pvz/{pvzId}/close_last_reception`, а не путь с настоящим id. Иначе каждый ПВЗ давал бы свой ряд метрик, и их число росло бы без конца. Запросы на несуществующие пути считаются вместе, под именем `unmatched`.
- Среди границ гистограммы есть 100 мс. Это цель по времени ответа из задания, и доля ответов быстрее неё считается точно.
- Бизнес-метрики: заведённые ПВЗ (по городам), открытые и закрытые приёмки, добавленные товары (по типам).
- Бизнес-счётчик растёт, только когда изменение уже записано в базу. Если транзакция откатилась, счётчик не меняется. Проверено так: 20 одновременных попыток открыть приёмку, успешна одна, и счётчик вырос на 1.
- Бизнес-логика не знает про Prometheus. Сервисы вызывают маленький интерфейс, а работа с Prometheus лежит в отдельном пакете `internal/metrics`.
- Есть и стандартные метрики Go и процесса: память, горутины, время CPU.

**IP клиента за прокси.** На сервере запросы приходят через Caddy, и адрес соединения у всех один: адрес Caddy. Настоящий IP Caddy пишет в заголовок `X-Forwarded-For`. Сервис читает этот заголовок, только если запрос пришёл с адреса из `TRUSTED_PROXIES`. Иначе клиент мог бы вписать туда любой адрес сам.

**Размер запроса.** Тело запроса не больше 1 МБ, иначе ответ 413. Самый большой запрос в API — пара полей JSON, так что лимит с большим запасом. Он защищает сервер от огромных запросов.

**Образ Docker** собирается в CI и публикуется в `ghcr.io/hollowkaeden/pvz-service`. Внутри только сам сервис: без shell и лишних программ (образ distroless), размер около 25 МБ. Сервис запускается не от root. Проверку здоровья для Docker делает сам бинарник командой `pvz healthcheck`, потому что curl в образе нет.

**Сброс демо.** Команда `pvz demo-reset` удаляет все ПВЗ, приёмки, товары и пользователей и создаёт заново небольшой набор: три ПВЗ, в Москве одна приёмка открыта. Набор создаётся через тот же код, что обрабатывает запросы, а не прямой записью в базу. На сервере сброс запускается каждую ночь.

**Страница с интерфейсом** открывается на `/`. На ней можно выбрать роль или войти по email, посмотреть список ПВЗ с фильтром и страницами, завести ПВЗ и пройти приёмку: открыть, добавить товары, удалить последний, закрыть. Рядом журнал (на широком экране справа, на узком внизу): каждый запрос к API с методом, путём, кодом ответа, временем и телами запроса и ответа. Страница не прячет API, а показывает его.

- Своих ручек у страницы нет: она вызывает те же ручки из контракта, что и Swagger UI.
- Без сборки и без npm: HTML, CSS и несколько JS-модулей в папке `web/`. Файлы встроены в бинарник, поэтому образ по-прежнему из одного файла.
- Свой внешний вид, не как у [портфолио](https://givemeanoffer.ru): тёмный интерфейс, похожий на рабочий инструмент склада. Шрифты системные, страница ничего не грузит со сторонних серверов.
- Регистрация на странице делает два запроса: `/register` заводит пользователя, а токен выдаёт следующий за ним `/login`. Роль пользователя страница читает из самого токена. Пароль в журнале запросов скрыт.
- Токен хранится до закрытия вкладки (`sessionStorage`). Если токен перестал действовать, страница просит войти заново.
- Данные из API вставляются на страницу как текст, а не как HTML. Заголовок `Content-Security-Policy` разрешает скрипты, стили и запросы только к своему серверу.

**Настройки** задаются только переменными окружения. Если настройки неверные, сервис сразу сообщает обо всех ошибках.
