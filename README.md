# pvz-service

Сервис для сотрудников пунктов выдачи заказов (ПВЗ): приёмка товаров. Решение открытого [тестового задания Авито для бэкенд-стажёров, весна 2025](https://github.com/avito-tech/tech-internship/blob/main/Tech%20Internships/Backend/Backend-trainee-assignment-spring-2025/Backend-trainee-assignment-spring-2025.md).

Учебный и портфолио-проект: в Авито решение не отправлялось.

> **Статус:** в разработке. Сервер запускается, все ручки из задания на месте, но пока отвечают `501` (не реализовано). Swagger UI открывается на `/docs/`.

## Запуск

Нужен Go 1.27+.

```bash
make run                      # или: go run ./cmd/pvz
curl localhost:8080/health    # {"status":"ok"}
```

Swagger UI: http://localhost:8080/docs/ (корень `/` ведёт туда же).

### Настройки

Только через переменные окружения. Без них сервис запускается с локальными значениями по умолчанию.

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `HTTP_ADDR` | `:8080` | адрес HTTP API |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |

## Разработка

```bash
make test       # unit-тесты с -race
make lint       # golangci-lint: формат и линтеры
make fmt        # gofmt + goimports
make generate   # кодогенерация (oapi-codegen), результат коммитится
make hooks      # один раз: pre-commit hook с линтером
```

golangci-lint ставится отдельным бинарником ([инструкция](https://golangci-lint.run/docs/welcome/install/)), версия v2.14.0, как в CI. Для `-race` нужен cgo: на Linux и macOS работает из коробки, на Windows нужен gcc (например, MinGW-w64).

Генератор кода указан в `go.mod` и запускается через `go tool`, поэтому ставить его отдельно не нужно, а версия везде одна.

CI (`.github/workflows/ci.yml`) на каждый push в `main` и PR запускает линтер и тесты, а ещё проверяет, что сгенерированный код совпадает со схемой.

## Контракт

- `api/openapi.yaml` — HTTP API. Это копия `swagger.yaml` из задания, она не меняется.
- `api/pvz.proto` — gRPC, тоже копия из задания.

Код HTTP-слоя генерируется из `openapi.yaml` командой `make generate` и лежит в `internal/transport/http/oapi`. Руками его не правят.

## Вопросы по заданию и решения

**Роли.** В тексте задания обычный пользователь называется `client`, а в swagger — `employee`. Я следую swagger: роли `employee` и `moderator`.

**Кодогенерация.** Задание просит генерировать DTO по схеме. Я использую [oapi-codegen](https://github.com/oapi-codegen/oapi-codegen): он генерирует не только DTO, но и разбор запросов и типы ответов. Поэтому ручка не может вернуть ответ, которого нет в схеме. Сгенерированные типы используются только в HTTP-слое, бизнес-логика работает со своими.

**Названия констант.** Города и типы товаров в схеме записаны по-русски, и генератор сделал бы константы вида `Москва`. Чтобы не менять схему, латинские имена (`CityMoscow`, `ProductTypeElectronics`) заданы в отдельном файле `oapi/overlay.yaml`. В JSON значения остаются русскими, как в задании.

**Ошибки.** Все ошибки возвращаются в формате из схемы: `{"message": "..."}`. Если запрос не удаётся разобрать (сломанный JSON, неверный UUID или дата), сервис отвечает 400. Непредвиденные ошибки пишутся в лог, а клиент получает 500 без подробностей.

**Swagger UI** открывается на `/docs/`. Это одна HTML-страница, скрипты грузятся с CDN. В схеме не указан адрес сервера, поэтому запросы из Swagger UI идут туда же, откуда открыта страница: и локально, и на демо-сервере.

**Остановка.** По сигналу остановки (например, `docker stop`) сервис перестаёт принимать новые запросы и даёт текущим до 8 секунд на завершение. Docker ждёт 10 секунд, так что сервис успевает остановиться сам.

**Логи** пишутся в JSON, по строке на запрос: метод, путь, статус, время ответа.

**Настройки** задаются только переменными окружения. Если настройки неверные, сервис сразу сообщает обо всех ошибках.
